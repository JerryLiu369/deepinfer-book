# 第 10 章 简报：投机解码：DSpark 与按置信度安排验证

## 在主线上的位置
技术篇第四章（★★）。回答主线三个源头之一与三：“模型结构（MTP）与生产高吞吐需求”。聚焦投机解码在大并发生产环境下的变长动态验证机制。内容属于 A 级源码与论文依据（arXiv 2607.05147）。

## 核心问题
草稿模型一次猜 5 个 token，每个请求都盲目验证 5 个到底划不划算？

## 读完能说出（三句话）
1. DFlash 草稿模块是一次非因果的双向注意力并行前向，而非多次自回归串行生成，3 个草稿层直接利用主干隐状态预测未来 5 个 token。
2. DSpark 创新性地引入置信度头，计算草稿 token 的联合存活概率，并结合 GPU 实测延迟曲线，动态为每个请求裁剪出边际收益最高的前缀长度。
3. 实测表明：在生产饱和并发（每卡 60 请求）下，变长验证将验证长度从 5 压缩至 3.2–4.4，换取 4–7% 的系统净吞吐提升；而在极低并发时固定开销占主导，吞吐会略微下降 1.5%。

## 小节结构
### 10.1 传统投机的困境：固定长度的算力浪费
- 问题：给每个请求都固定验证 5 个 token，为什么在生产大并发下会拖慢整体速度？
- 思路：一旦第 1 或第 2 个 token 被拒，后续已算完的 3–4 个 token 算力全部白费；在大批次下，总 token 预算迅速逼近显存带宽与算力瓶颈。
- 做法：分析固定验证在不同接受率下的浪费率模型。
- 代价：显存流量被无效验证大量侵占。
- 对比：固定步长投机 vs 动态自适应验证。
- 用到的事实：R09-#1, R09-#6

### 10.2 DFlash：非因果并行草稿生成
- 问题：草稿 token 是如何以极低代价生成的？
- 思路：DFlash（arXiv 2602.06036）采用块内双向注意力，一次 Forward 产出 5 个位置的草稿特征。
- 做法：分析 `dflash.py` 的输入拼接 `[golden, noise×4]` 与跨层残差聚合。
- 代价：块内缺乏单向因果约束，依赖采样时的马尔可夫头打补丁。
- 对比：自回归小模型（EAGLE）多次前向 vs DFlash 单次块并行前向。
- 用到的事实：R09-#1, R02c-#3

### 10.3 DSpark 核心：置信度头与边际收益曲线
- 问题：如何事先知道一个草稿 token 能不能被接受？
- 思路：DSpark（arXiv 2607.05147）训练了专门的置信度头输出接受概率，累乘得到生存曲线。
- 做法：剖析 `mtp_varlen.hpp` 与 `schedule_mtp_varlen.py`，展示以每毫秒期望产出 token 数最大化为目标的求解算法。
- 代价：增加微量置信度前向与调度评估耗时。
- 对比：规则启发式裁剪 vs 期望吞吐全局最优求解。
- 用到的事实：R09-#2, R09-#3, R09-#4

### 10.4 数据表深度拆解：为什么低并发亏、高并发赚
- 问题：官方实测数据显示 16 并发下吞吐下降 1.5%，而 60 并发下提升 4–7%，背后机理是什么？
- 思路：低并发处于 Memory-Bound 区域，“空槽位算力近乎免费”，裁剪带来的时间节省抵不过微量接受率损失；高并发处于 Compute-Bound 区域，CUDA Graph 档位大幅跨越，算力立竿见影释放。
- 做法：逐行解读官方 Q&A 实验表格，推导步耗时与 Graph 桶跃迁物理过程。
- 代价：低负载场景下应主动关闭变长验证。
- 对比：脱离并发谈投机收益 vs 基于工作点区间的精准定性。
- 用到的事实：R09-#6, R16-#2

### 10.5 vLLM 和 SGLang 怎么做
- 问题：通用引擎如何支持 DSpark？
- 思路：vLLM 引入了 Adaptive Verification PR，SGLang 在 V4.1 方案中移植了 DSpark 延迟校准内核。
- 做法：对比各框架在变长投机与 CUDA Graph 结合处的实现差异。
- 代价：通用框架需要适配多种不同类型的草稿头。
- 对比：通用投机解码器框架 vs DeepInfer 内置 DSpark。
- 用到的事实：R13-#5, R14-#7
