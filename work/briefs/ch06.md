# 第 6 章 简报：调度：让 GPU 一刻不停

## 在主线上的位置
技术篇第一章（★★）。回答主线三个源头之三：“生产要什么——极低延迟与高吞吐”。聚焦 CPU 调度与 GPU 计算的重叠流水线。内容属于 A 级源码事实（示范章扩展）。

## 核心问题
CPU 的调度计算怎样才能完全不让 GPU 产生等待气泡？

## 读完能说出（三句话）
1. 零开销异步调度（ZOS）让 CPU 在 GPU 执行第 N 步时提前安排第 N+1 步前向，彻底抹平了 Decode 阶段 GPU 等待 CPU 的空闲气泡。
2. 在异步调度下，未知采样结果与投机验证长度被移交给 GPU 原生 TileLang 算子修正，保证了流水线的无阻塞推进。
3. 开源版 Prefill 调度采用贪心分块策略，直接受限于上下文预算与 CP 对齐，未包含生产环境文档描述的二次代价模型。

## 小节结构
### 6.1 同步调度的致命软肋：GPU 气泡
- 问题：常规调度每步串行执行“调度 → 前向 → 采样 → 后处理”，GPU 为何会频繁空等？
- 思路：解码步耗时极短（几毫秒），CPU 到 GPU 的跨主机同步与 Python 后处理占比过大。
- 做法：绘制同步时序图，量化 GPU 空闲占比。
- 代价：硬件利用率大幅打折，无法打满 GPU 算力。
- 对比：传统串行调度 vs 重叠流水线。
- 用到的事实：R05-#1, R05-#2

### 6.2 ZOS 零开销异步调度：让 CPU 跑在前面
- 问题：GPU 尚未跑完当前步，CPU 如何提前排定下一步？
- 思路：将同步点后移，CPU 始终后处理 N-1 步，并将 N+1 步的前向指令提前塞入 GPU 流。
- 做法：剖析 `worker.py` 与 `csrc/engine/zos.cpp`，展示两条交错的时间线与 `remap` 映射表。
- 代价：请求结束感知延迟一步，可能导致已结束请求多跑一步无用 forward。
- 对比：标准异步执行 vs ZOS 双步流水线。
- 用到的事实：R05-#2, R05-#3

### 6.3 异步调度与投机解码的协同
- 问题：ZOS 提前调度时并不知道草稿 token 的接受率，验证预算如何分配？
- 思路：CPU 只定总 token 预算，GPU 内部用 TileLang 内核根据置信度动态重排 `seqlens_q`，并保持总和不变。
- 做法：分析 `schedule_mtp_varlen.py` 算子与 pinned 缓冲更新。
- 代价：需在 GPU 上执行额外轻量修正算子。
- 对比：CPU 严格预分配 vs GPU 动态就地修正。
- 用到的事实：R05-#4, R09-#2

### 6.4 Prefill 分块与算力记账真相
- 问题：文档宣称的“二次代价模型按时间预算精确求解分块”在代码中是如何落地的？
- 思路：求证开源代码事实：开源版未包含 `compute_quota_limit`，代码中的二次项仅用于统计 MFU 的 FLOPs 记账。
- 做法：展示开源版 `min(prompt, quota)` 贪心分块逻辑，诚实指出与文档描述的差异。
- 代价：缺乏根据网络动态延迟实时自适应调整 Prefill 块的能力。
- 对比：开源版启发式分块 vs 生产版二次代价优化。
- 用到的事实：R05-#5, R12-#3

### 6.5 vLLM 与 SGLang 怎么做
- 问题：主流框架如何处理调度重叠？
- 思路：SGLang 较早提出 Overlap Scheduler，vLLM V1 引入 `-1` 占位 token 异步调度。
- 做法：对比三者在异步流水线触发条件与投机解码适配上的异同。
- 代价：通用框架需兼容百种模型，难以像 DeepInfer 一样把模型特化逻辑深埋进 GPU。
- 对比：SGLang 三流事件驱动 vs DeepInfer 专用 ZOS。
- 用到的事实：R13-#2, R14-#2
