# 第 7 章 简报：KV cache 与状态缓存

## 在主线上的位置
技术篇第二章（★★）。回答主线三个源头之一与三：“模型结构（多级KV）决定显存管理”。剖析显存中 5 类缓存的物理布局与极致量化。内容属于 A 级源码事实与数学推导。

## 核心问题
面对 V4.1-Flash 的复杂多形态 KV，DeepInfer 如何在有限显存内实现极高密度管理？

## 读完能说出（三句话）
1. 显存缓存分为分页存储的块状 KV（890 B/token）和单序列固定槽位的 SWA 状态缓存（528 B/token/层，环形窗口 134），两者生命周期完全不同。
2. 块状 KV 采用激进的 FP4（E2M1+E4M3）与 MXFP4 低精度量化，1M 超长上下文仅需 890 MiB 显存，这是跨数据中心传输与长时间持久化的前提。
3. 开源版本未内置自动前缀树匹配，前缀复用通过显式 `fork_seq` 引用计数共享块，接口预留给外部 3FS 存储集群。

## 前置知识
第 3 章关于 890 字节 KV 推导与 SWA 窗口，第 1 章关于 KV Cache 基础。

## 小节结构
### 7.1 五类缓存的物理全景
- 问题：一个模型内部为何需要同时管理 5 种不同格式与周期的缓存？
- 思路：解耦主注意力、稀疏索引、局部滑动窗口与边界累加状态。
- 做法：系统拆解 `ca_cache`、`ica_cache`、`swa_cache`、`ca_state`、`ica_state` 的张量形状与内存布局。
- 代价：显存管理器需双轨并行维护两套 BlockManager。
- 对比：通用引擎单一张量池 vs DeepInfer 异构多缓存区。
- 用到的事实：R06-#1, R06-#2

### 7.2 块状 KV：128 token 对齐与 FP4 压缩
- 问题：为什么每块必须硬编码为 128 token？890 字节如何在物理字节流中存放？
- 思路：128 token 与底层的张量对齐单位（TMA/UB）强行匹配，避免碎片。
- 做法：分析 `cache_engine.py` 的扁平 uint8 连续切段与 32B 跨层步长对齐。
- 代价：小于 128 token 的请求尾部存在微量显存填充浪费。
- 对比：vLLM 16/32 动态 block_size vs DeepInfer 强制 128 对齐。
- 用到的事实：R06-#1, R06-#4

### 7.3 StateBlock：SWA 状态槽与 134 环形缓冲
- 问题：SWA 窗口为 128，为什么状态缓存槽要留出 134 个位置？
- 思路：134 = 128（滑动窗口） + 6（最大投机回退步长 `nextn + 1`），保证回退时不越界。
- 做法：展示 `StateBlock` 存储区（前 20 层）、丢弃区（后 20 层）与环形重排算子。
- 代价：单序列预留固定槽位，存在静态显存开销。
- 对比：全历史滑动截断 vs 静态固定环形槽。
- 用到的事实：R06-#3, R07-#4

### 7.4 显存容量规划与前缀命中真相
- 问题：显存空间如何自动在模型权重、激活值与 KV cache 之间切分？开源版有前缀缓存吗？
- 思路：多 rank 取平均显存后保留安全余量；开源版无 Hash 树，仅预留 `fork_seq` 接口。
- 做法：剖析 `profile_num_available_blocks` 计算公式与前缀注入插槽。
- 代价：无法单机开箱享受跨 Session 前缀自动命中。
- 对比：vLLM Block Hash / SGLang RadixTree vs DeepInfer 外置 3FS 显式注入。
- 用到的事实：R06-#5, R06-#6

### 7.5 vLLM 和 SGLang 怎么做
- 问题：通用框架如何支持多级混合 KV？
- 思路：vLLM 采用 Unified Cache 与 Block Hash；SGLang 升级为 UnifiedRadixCache。
- 做法：对比三者在 SWA 混合缓存与外部存储对接的实现深度。
- 代价：通用框架的抽象层使其难以在单 token 字节数上压到 890 字节的极致。
- 对比：树状自适应管理 vs 硬件写死内存拓扑。
- 用到的事实：R13-#3, R14-#3
