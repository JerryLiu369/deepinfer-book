# 第 1 章 简报：推理引擎在做什么

## 在主线上的位置
全书背景铺垫章节。回答主线中的第一个问题：从单次模型跑通到大规模在线服务，底层面临哪些物理与算力瓶颈。为全书奠定 prefill/decode、KV cache、吞吐-延迟权衡等基础语汇。内容属于行业通用概念打底。

## 核心问题
从“跑一次模型”到“一天服务 155 万亿 token”，中间隔着哪些核心系统问题？

## 读完能说出（三句话）
1. 推理过程分为算力受限的 prefill（输入处理）阶段与显存带宽受限的 decode（逐 token 生成）阶段。
2. KV cache 是大模型推理中最核心的显存开销，其存储格式、生命周期与复用效率直接决定了系统的服务成本。
3. 推理引擎的核心任务是在吞吐量、首字延迟（TTFT）与每字间隔（TBT）之间寻求极致平衡，手段包括批处理、张量/专家并行、投机解码与底层定制内核。

## 前置知识
读者需了解 Transformer 基本结构与自注意力机制（Q/K/V 矩阵乘法）。无需提前掌握分布式推理或 PagedAttention 细节，本章提供基础定义。

## 小节结构
### 1.1 大模型推理的两个阶段：Prefill 与 Decode
- 问题：为什么同一个模型在处理用户输入时飞快，而在逐字生成回答时却受到显存带宽死死卡死？
- 思路：Prefill 具有大矩阵计算密度（compute-bound），Decode 具有单 token 向量访存特征（memory-bound）。
- 做法：分别建立算力受限与带宽受限的屋顶模型（Roofline Model），明确 TTFT 与 TBT 的物理差异。
- 代价：Prefill 与 Decode 混合调度会相互挤占算力与显存带宽。
- 对比：传统引擎单机混部 vs 现代系统（如 DeepSeek E/P/D）物理分离部署（引出第 4 章）。
- 用到的事实：R01-#4, R13-#2, R16-#1

### 1.2 显存黑洞：KV Cache 为什么决定成本
- 问题：为什么长文本生成时显存会被迅速吃光？不缓存历史 KV 行不行？
- 思路：自回归生成必须保留历史 Key 和 Value，否则每步都需要从头全量重算。
- 做法：分析随上下文线性增长的显存消耗公式，给出标准模型与压缩模型的显存对比。
- 代价：显存容量上限直接卡死单卡最大并发请求数（Batch Size）。
- 对比：vLLM 的 PagedAttention 显存分页 vs DeepSeek 的 FP4 块状 KV 与 SWA 状态存储（引出第 7、8 章）。
- 用到的事实：R02a-#1, R06-#1, R13-#3

### 1.3 批处理与调度：Continuous Batching 的演进
- 问题：静态批处理（Static Batching）会导致短请求等待长请求，造成严重的 GPU 算力气泡。
- 思路：以 token 或步（iteration）为颗粒度动态纳管请求进出（Continuous Batching）。
- 做法：展示动态调度器每步插入新请求与回收结束请求的时序图。
- 代价：调度开销大幅上升，CPU 调度延迟可能反噬 GPU。
- 对比：vLLM V1 调度 vs SGLang Overlap vs DeepInfer ZOS 零开销异步调度（引出第 6 章）。
- 用到的事实：R04-#2, R05-#2, R13-#2, R14-#2

### 1.4 并行、投机与内核：压榨硬件的三把斧
- 问题：单卡显存装不下大模型 MoE 权重，且单 token 生成延迟无法满足人类阅读需求。
- 思路：并行切分模型参数、用小草稿模型多猜几个 token、用手写汇编算子逼近硬件理论极限。
- 做法：概括专家并行（EP）、投机验证与专用内核（FlashMLA/DeepGEMM）的作用边界。
- 代价：并行引入网络通信开销，投机解码可能因验证失败浪费算力。
- 对比：通用方案（TP/PP）与 DeepSeek 纯 EP-MoE + DSpark 变长验证的选择差异（引出第 9、10、11 章）。
- 用到的事实：R08-#1, R09-#1, R10-#1
