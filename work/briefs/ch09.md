# 第 9 章 简报：并行：注意力用数据并行，专家用专家并行

## 在主线上的位置
技术篇第三章（★★）。回答主线三个源头之二：“系统怎么部署——大规模分布式切分”。聚焦超大规模 MoE 在数十张甚至上百张卡上的并行切分、通信优化与动态负载均衡。内容属于 A 级源码与 Q&A 事实。

## 核心问题
一个拥有 384 个专家的超大 MoE 模型，如何拆分到 64–128 张 GPU 上，同时避免木桶效应和通信拥堵？

## 读完能说出（三句话）
1. DeepInfer 采用“Attention 用数据并行（DP），MoE 用专家并行（EP）”的正交切分策略，两者的并行度严格相等，彻底摒弃了张量并行（TP）。
2. 宽专家并行（Wide-EP，EP64–128）在 Decode 阶段能将单步权重访存流量压低 7 倍以上，配合 DeepEP 高效通信库实现跨卡分发。
3. 专家负载均衡器（EPLB）通过冗余专家复制与两级贪心算法动态修正热门专家热点，在 NVLink 域内利用对称内存（`symm_mem`）实现零等待权重搬运。

## 小节结构
### 9.1 混合切分：DP-Attention 配合 EP-MoE
- 问题：为什么不给注意力做张量并行（TP），而要让每个卡独立跑自己的请求？
- 思路：MLA 极度压缩了 KV 头数，TP 无法有效切分；Attention 用 DP 保证各卡完全本地计算，仅在 MoE 处做全互联分发。
- 做法：分析全局 Rank 映射公式 `((replica*dp+r)*cp+c)`，剖析各 DP rank 自主 Padding 与步型同步。
- 代价：MoE 层前后的 All-to-All 通信（Dispatch/Combine）成为绝对吞吐瓶颈。
- 对比：传统 TP+EP 混合并行 vs 纯 DP-Attention + Wide-EP。
- 用到的事实：R08-#1, R08-#2, R08-#3

### 9.2 Wide-EP：宽专家并行的算力账本
- 问题：把专家拆在 8 张卡和拆在 64 张卡上，计算与访存有何本质不同？
- 思路：Decode 阶段受显存带宽限制，EP 越大，每张卡需要加载的专家权重越少（EP64 每卡仅 7 个专家 vs EP8 每卡 52 个专家）。
- 做法：推导 EP8 vs EP64 访存流量下降 7.43 倍的物理过程，解释为什么步耗时通信占比提升但整体吞吐仍提升 5–53%。
- 代价：跨机网络必须依赖高带宽非阻塞 RDMA 拓扑。
- 对比：小规模稠密部署 vs 超节点大规模稀疏切分。
- 用到的事实：R08-#1, R16-#3

### 9.3 动态调度：EPLB 算法与 NVLink 权重搬运
- 问题：不同请求可能高频命中同一个“网红专家”，导致某些 GPU 算力过载而其他 GPU 闲置（负载不均）。
- 思路：EPLB 在每张卡上保留冗余专家槽位，根据在线统计命中率把热门专家复制到空闲卡上。
- 做法：分析 `deepinfer/model_executor/eplb/policy.py` 的两级贪心装箱算法，以及 `shuffle.py` 通过 `symm_mem` 进行 CUDA IPC 直读。
- 代价：冗余专家会消耗额外的静态 GPU 显存。
- 对比：静态专家分配 vs 在线热度自适应重排。
- 用到的事实：R08-#5, Q01

### 9.4 因果平衡：Mirror CP 上下文并行
- 问题：长文本 Prefill 使用上下文并行（CP）时，因果自注意力的下三角结构导致后半段卡计算量远大于前半段卡。
- 思路：采用 Mirror CP（Zigzag 镜像分配），把序列首尾两段交错配对给同一个 Rank。
- 做法：分析 `tilelang_ops/prepare_cp_mirror.py` 的对偶块划分，实现跨卡计算量精确对齐。
- 代价：通信需要额外的切块分发与重组逻辑。
- 对比：传统单调切分 vs 镜像对称切分。
- 用到的事实：R08-#4

### 9.5 vLLM 和 SGLang 怎么做
- 问题：通用框架是否支持 Wide-EP 与 EPLB？
- 思路：SGLang 较早开源了 DP-Attention 与 DeepEP 集成；vLLM 引入了 DEP 并行模式与外部 EPLB 配方。
- 做法：对比三者在 MoE 通信融合与重平衡调度上的代码实现。
- 代价：通用框架需要兼顾不同网络环境，无法硬编码特定的 NVLink 拓扑。
- 对比：框架通用通信抽象 vs DeepInfer 专用硬件绑定。
- 用到的事实：R13-#4, R14-#4
