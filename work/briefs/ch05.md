# 第 5 章 简报：代码地图：仓库结构与一个请求的一生

## 在主线上的位置
全书第三大核心章节（★★★）。带领读者真正踏入代码仓库，建立代码空间分布认知与单次推理执行流全景。内容属于 A 级源码证据。

## 核心问题
打开 DeepInfer 仓库，应该从哪里读起？一次 `LLM.generate()` 调用在代码底层经历了什么？

## 读完能说出（三句话）
1. DeepInfer 呈现“Python 控制面 + C++ 调度执行核 + TileLang 双硬件算子库”的三层清晰架构，C++ 调度器通过 pybind11 导出。
2. 进程模型为单机每卡一个 Worker 进程，Driver 与 Worker 之间通过无名共享内存环（SHM MessageQueue）实现零开销广播控制，采样仅在 Driver 端发生。
3. 一次推理请求沿 `entrypoints` → `engine` → `worker` → `model_runner` → `model_executor` → 内核依次流转，Decode 阶段使用 CUDA Graph 覆盖主模型前向。

## 前置知识
第 2 章关于离线接口的说明，第 3 章关于模型各层结构。

## 小节结构
### 5.1 仓库全景目录与模块分工
- 问题：近 6 万行代码分布在各个目录，各层如何分工？哪些自研，哪些继承？
- 思路：建立“入口 → 引擎 → 工作进程 → 模型执行 → 算子与驱动”的清晰分层地图。
- 做法：给出详细目录职责表（`entrypoints/`、`engine/`、`csrc/`、`tilelang_ops/` 等）及代码行数统计。
- 代价：C++ 与 Python 跨语言边界带来调试难度。
- 对比：vLLM 纯 Python 调度 vs DeepInfer C++ 调度核。
- 用到的事实：R03-#1, R03-#2, R03-#3

### 5.2 进程模型与共享内存广播
- 问题：多 GPU 分布式环境下，CPU 调度指令如何毫秒级同步给所有 Worker 且不卡死 GIL？
- 思路：单 GPU 独立 Worker 进程，Driver 线程通过 1 MiB 循环共享内存无锁广播指令。
- 做法：分析 `shm_broadcast.py` 与 `MessageQueue` 实现，展示广播无返回值的异步设计。
- 代价：控制面缺乏强同步确认，异常处理需靠全局标志。
- 对比：PyTorch RPC / Ray Actor vs 裸共享内存环。
- 用到的事实：R04-#1, R04-#2

### 5.3 追踪一次 generate：从入口到返回
- 问题：调用 `LLM.generate(prompts)` 时，数据结构如何变形？前向与采样在何处闭环？
- 思路：步步追踪代码调用栈，从 Python 对象到 C++ Sequence 结构体再到 GPU Tensor。
- 做法：逐步列出文件与函数签名（`llm.py:generate` → `llm_engine.py:step` → `worker.py:execute_model` → `model_runner.py`）。
- 代价：复杂的状态转换增加代码阅读心智负担。
- 对比：同步递归调用 vs 状态机轮询。
- 用到的事实：R04-#1, R04-#3, R04-#4

### 5.4 性能护甲：CUDA Graph 与硬件拓扑绑定
- 问题：每步小 batch 解码时，PyTorch Kernel Launch 开销远大于计算耗时，如何消除？
- 思路：用 CUDA Graph 将整步前向录制为单图，按 token 数分档匹配；用 `deep_cluster` 绑定 CPU/NUMA 亲和性。
- 做法：剖析 `cuda_graph_runner.py` 与 `dflash_cuda_graph_runner.py` 的录制与重放逻辑。
- 代价：显存需要静态预分配各档位 Graph 内存池。
- 对比：纯动态 Launch vs 档位静态图重放。
- 用到的事实：R04-#5, R04-#7
